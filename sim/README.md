# sim — PC 端仿真

在没有目标硬件的情况下验证感知层算法与玩法逻辑。
**杠杆很大：调一次参数在硬件上要一天，在这里是几秒。**

零第三方依赖，系统 python3 即可（已在 3.9.6 验证）。

## 模块

| 文件 | 内容 |
|---|---|
| `sensing.py` | 加权 Jaccard 匹配、8 槽 LRU 地点记忆、迟滞状态机、移动量累积 |
| `gameplay.py` | OUI/SSID 语义映射、biome 分类、确定性刷新、三条状态轴 |
| `replay.py` | 回放采集数据，输出感知层判定 |
| `prototype.py` | 玩法原型，输出模拟游玩报告 |

`sensing.py` 刻意写成**固件的参考实现** —— 无浮点必需、无动态分配、状态量定长，
以便后续用定点整数移植到 ESP32-C3。

## 用法

```bash
# 回放真实采集
python3 sim/replay.py data/raw/day1.ndjson --only-24g
python3 sim/replay.py data/raw/*.ndjson -v          # 逐次扫描明细

# 玩法原型（无采集数据时用合成日节律）
python3 sim/prototype.py --synthetic --days 7
python3 sim/prototype.py data/raw/day1.ndjson --only-24g
python3 sim/prototype.py --synthetic --no-care      # 验证消沉不清零
python3 sim/prototype.py --synthetic --days 1 -v    # 打印每次遭遇
```

> **`--only-24g` 强烈建议开启。** 电脑能看 5GHz，
> 而 [ESP32-C3 只有 2.4GHz](../docs/01-constitution.md#11-硬约束清单)。
> 实测本机 61 个 AP 里只有 17 个是 2.4G —— 不加这个参数，
> 你看到的 AP 密度会是设备实际能看到的三倍多。

## 调参入口

| 参数 | 位置 | 作用 |
|---|---|---|
| `MATCH_THRESHOLD` | `sensing.py` | 地点匹配阈值。调高→同一地点被拆成多个 |
| `MOVE_THRESHOLD` | `sensing.py` | 移动判定阈值。调低→静坐被误判为移动 |
| `HYSTERESIS` | `sensing.py` | 状态切换需连续几次一致。调高→抗噪但迟钝 |
| `*_DECAY_PER_HOUR` | `gameplay.py` | 三条状态轴的衰减速率 |
| `BASE_SPAWN_INTERVAL` | `prototype.py` | 基地遭遇间隔 |

**这些值目前全是估算，必须用真实口袋数据重新标定**
（[docs/02-sensing.md#26](../docs/02-sensing.md#26-口袋标定一个会坑人的实测陷阱)）。

## 原型跑出来的三个真实问题

这些不是设计时想到的，是跑了 7 天合成数据后暴露的 ——
**这正是先做原型的价值**。

### ① 一天照料一次抵不过衰减

初版模拟玩家每天早上喂一次，结果七天后饱食归零、心情单调递减到 12。

改为**一天三次**（每 8 小时一个窗口）后状态健康。
这与「[一天摸设备五次、每次 30 秒](../docs/01-constitution.md#12-由约束推导出的核心形态)」
的形态设定一致 —— 说明衰减速率应当按真实使用频率来配，而不是凭感觉。

### ② 基地遭遇曾经完全为零

初版把基地遭遇挂在「移动量攒够」上，而移动量只在移动时增长 ——
**结果驻留时永远不触发，基地形同虚设**。

修法是基地按**时间**排程。这正好印证了
[docs/02-sensing.md#20](../docs/02-sensing.md#20-核心取向wifi-是上下文开关不是内容生产者)
的核心取向：**让时间生产内容，空间调制内容**。
否则窝在家里一整天将毫无产出，而「设备永远不会没东西可看」是这个设计要保证的事。

### ③ 迟滞机制会让通勤第一帧被误建成地点

7 天合成数据（只有家和公司两个驻留点）却建出了 **8 个地点**。

原因很微妙：迟滞要求连续 2 次才切换状态，所以**移动的第一帧 `state` 仍是 `staying`**，
于是那一帧的指纹被当成「新地点」记了下来 —— 每次通勤都记一个。

修法是同时看原始距离：`state != MOVING and dist <= MOVE_THRESHOLD`。
距离本身就超阈值时即时否决，不等迟滞确认。修完地点数降到 2 个，正确。

> 这个 bug 在真实硬件上同样会发生，而且**在设备上极难发现** ——
> 只会表现为「地点表莫名其妙被塞满」。提前在 PC 上撞到它，省了不知多少调试时间。

## 怎么判读结果

`replay.py` 与 `prototype.py` 都会在末尾打印判读提示。要点：

**感知层**
- 地点数应是 3~5 个。远多于此 = 阈值太严或有误建
- 状态转换应 < 2 次/小时。真实生活一天只有 2~4 次（家→通勤→公司）
- 单一地点采集时，状态应几乎全是驻留、地点数为 1

**玩法**
- 遭遇 10~30 次/天较合适
- 照料模式下不该长期消沉；不照料时**应能消沉但探索值不清零**
- 主宠属性应在 TOP5 里 —— 验证「今天带谁出门」是个真决策
- ★★★★★ 应当罕见（< 5%）

## 合成数据的局限

`--synthetic` 编的是「家 → 通勤 → 公司 → 通勤 → 家」的理想日节律，
AP 分布是人造的。它能验证**逻辑与调参**，但不能替代真实采集：

- 真实环境的 AP 会随机出现和消失（邻居设备开关机）
- 真实 RSSI 抖动远大于合成数据
- 真实通勤不是「AP 全换」而是渐变

所以定性结论（「家和公司能不能分开」）必须用
[真实采集数据](../tools/collector/README.md)来回答。
