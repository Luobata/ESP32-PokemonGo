# ESP32 嵌入式开发框架

> 这份文档抽象自一个真实项目（ESP32-C3 + 240×320 屏 + 三个按键的掌机游戏，
> 七轮迭代、十一个宿主门禁、两个由用户实测发现的缺陷）。
>
> **但它不是那个项目的回顾。** 目标是：**一个没读过那个项目代码的人，
> 能照着它搭起同样的验证体系。** 举例会引用具体文件行号作为证据，
> 但每条结论都写成脱离该项目也成立的形式。
>
> 读法建议：先读第一章（问题），它决定了后面所有设计的取舍。
> 如果只有十分钟，读第一章 + 第四章（观测判断清单）+ 第九章（成本）。

---

## 第一章 这套东西解决什么问题

### 1.1 嵌入式开发的核心困难是观测困难

写 Web 或后端时，验证靠的是一套成熟的观测手段：断点、REPL、单元测试、
日志、错误栈。这些手段的共同前提是**你能在故障发生的位置停下来看**。

嵌入式（这里特指 MCU 类，无操作系统或仅有 RTOS）几乎全部缺失：

| 常规手段 | 在 MCU 上的状况 |
|---|---|
| 断点 | 有 JTAG 但代价高；停下来的瞬间 DMA/定时器/射频还在跑，停了就不是原状 |
| REPL | 没有。想试一个值要改代码 → 编译 → 烧写，一轮几十秒到几分钟 |
| 单元测试 | 代码 include 了平台头文件就编不进宿主，测不了 |
| 错误栈 | 很多故障不抛异常。**「屏幕显示不对」没有栈** |
| 日志 | 有，但串口带宽有限，且日志里没有像素 |

**最要紧的一条是最后两条的组合**：嵌入式的故障形态大量是
「输出不对」而不是「程序崩了」。屏幕花了、声音断了、数值偏了 ——
这些**不产生任何异常信号**。没有人报错，你就不知道该看哪里。

### 1.2 由此推出的三条设计原则

框架的每一条做法都是从 1.1 推出来的，不是审美偏好：

**原则 A：能在宿主上验的，绝不留到设备上验。**
设备上一轮几十秒且观测能力弱；宿主上一轮几百毫秒且工具齐全。
**推论**：逻辑必须与平台解耦到「宿主可编译」的程度（第二章）。

**原则 B：能在编译期挡住的，绝不留到运行期。**
运行期在设备上，而设备上你看不见。
**推论**：不变量要写成 `_Static_assert` 而不是注释（第五章）。

**原则 C：观测手段必须能看见目标故障 —— 这一条要显式验证。**
「测了没问题」和「测不到问题」在报告里长得一模一样。
**推论**：每个验证手段都要回答「如果这里坏了，我这个手段会变吗」（第四章）。

### 1.3 什么规模的项目值得这么做

**先说不值得的**（避免读者照抄到不合适的地方）：

- **点灯、读传感器发 MQTT 这类几百行的项目**：不值得。
  逻辑简单到目视可验，建这套东西的成本远超收益。
- **一次性 demo、验证性原型**：不值得。它的生命周期短于框架的摊销周期。

**值得的判据**（满足两条以上）：

1. **有可对账的数值逻辑** —— 状态机、曲线、判定表、序列化格式。
   这类东西「差一点」不会崩，只会一直错，是宿主对账的主战场。
2. **有呈现层**（屏幕/声音/灯效）—— 故障形态是「不对」而非「崩」。
3. **生命周期超过几周**，或**要交给别人接手**。
   框架的主要收益是「下一轮不用重新验」，短命项目拿不到这个收益。
4. **有一份可作基准的参考实现**（PC 侧模型、上一代产品、协议规范）。
   没有基准，逐值对账无从谈起（第八章会讲基准本身缺失的风险）。

成本的量化在第九章。

## 第二章 纯模块模式 —— 整套框架的前提

### 2.1 问题

`#include "esp_log.h"` 或 `#include "freertos/FreeRTOS.h"` 一旦出现在
某个 `.c` 里，这个文件就**只能在目标平台编译**。于是它的逻辑
只能靠烧写验证 —— 回到第一章那个几十秒一轮、观测能力弱的循环里。

### 2.2 做法：把逻辑与平台切开成两层

```
纯逻辑层（pure）      不 include 任何平台头。只有 stdint/stdbool/string。
                     状态机、曲线、判定、序列化。
                     ── 宿主 cc 可直接编译 → 可逐值对账

平台层（platform）    FreeRTOS 任务、锁、NVS、外设驱动、UI 框架。
                     只做「搬运与调度」，不含可对账的判断逻辑。
                     ── 只能在设备上验
```

**判据很硬**：纯逻辑层的头文件里，平台 include 数必须为 **0**。
这是可机械检查的（第五章会把它变成门禁）。

参考项目的实测：九个纯模块头文件
（`exp.h` `party.h` `opening.h` `transition.h` `audio.h`
`battle.h` `capture.h` `encounter.h` `nurture.h`）
平台 include 全部为 0，总 include 数 1~3（只有 `stdint.h` 一类）。

### 2.3 可照抄的骨架

**纯模块头文件模板**：

```c
// mymodule.h —— <一句话说清这个模块算什么>
//
// ## 接口约定（不要删这段）
// 本头文件**不得 include 任何平台头**（esp_*、freertos/*、driver/*、
// nvs_*、UI 框架）。宿主门禁 include 本模块的 .c 直接编译，
// 一旦引入平台依赖，门禁立刻编不过 —— 那是有意的保护。
#pragma once
#include <stdint.h>
#include <stdbool.h>

#define MY_LEVEL_MAX 100          // 常量也要能被门禁读到，别藏在 .c 里

// 纯函数：同输入必同输出，无静态状态、无 I/O、无时间依赖。
uint32_t my_curve(uint8_t n);
uint8_t  my_inverse(uint32_t v, uint8_t cap);   // cap 参数即便暂时无用也保留
```

**关键细节，都是踩过的**：

- **常量放头文件**，不要藏在 `.c` 的 `static const`。门禁要对账常量本身
  （「除数抄错」这类缺陷只有对常量才抓得住）。
- **纯函数不要有静态状态**。有状态的部分留在平台层。
  状态一进纯模块，宿主对账就要构造状态，成本翻倍。
- **暂时没用的参数也保留**（如上面的 `cap`）。参考项目里
  `exp_to_level(exp, cap)` 的 `cap` 是为后续功能留的，
  契约里专门标注「不可删」—— 否则下一个人会当冗余删掉，
  等要用时接口已经变了。

**宿主驱动模板**（门禁脚本内嵌的 C 主程序）：

```c
#define HOST_BUILD 1
#include <stdio.h>
#include <stdint.h>
#include <string.h>

/* 用**真的** .c，不要写替身实现 ——
   替身一旦与真的不同，对账全绿而固件全错。
   这是整个门禁体系里最容易犯且后果最大的错。 */
#include "mymodule.c"

int main(void) {
    char cmd[32];
    while (scanf("%31s", cmd) == 1) {          // 简单的行协议：命令 + 参数
        if (!strcmp(cmd, "cv")) {              // curve
            unsigned n; if (scanf("%u", &n) != 1) break;
            printf("%u\n", (unsigned)my_curve((uint8_t)n));
        } else if (!strcmp(cmd, "cst")) {      // constants
            printf("%d\n", MY_LEVEL_MAX);
        }
        fflush(stdout);                        // 必须 flush，否则 Python 侧读不到
    }
    return 0;
}
```

**门禁脚本骨架**：

```python
#!/usr/bin/env python3
"""mymodule.c 与 <基准> 的逐值对账。

用法： python3 tools/verify_mymodule.py [mymodule.c 路径]
默认对账真实路径；**传入别的路径用于反向验证** ——
把副本改坏再跑，脚本必须红，证明它真在对账而不是恒绿。
"""
import os, subprocess, sys, tempfile

DRIVER = r"""<上面那段 C>"""

def build(src_dir, tmp):
    exe = os.path.join(tmp, "drv")
    cmd = ["cc", "-O1", "-Wall", "-Wextra", "-Werror",
           "-I", src_dir, "-o", exe, os.path.join(tmp, "drv.c")]
    r = subprocess.run(cmd, capture_output=True, text=True)
    if r.returncode: sys.exit("宿主编译失败：\n" + r.stderr)
    return exe

def main():
    fails = []
    # 1) 常量对账 —— 先验常量，常量错了后面全错
    # 2) 全域/边界逐值对账（见 2.4 的覆盖设计）
    # 3) 汇总
    if fails:
        for f in fails[:40]: print("✗", f)
        print(f"\n{len(fails)} 处不符"); return 1
    print("✅ 全部一致"); return 0

sys.exit(main())
```

`-Werror` 不是洁癖：宿主编译比目标编译更严，
能顺手抓到目标编译放过的隐式转换与未初始化。

### 2.4 覆盖怎么设计：逐值 > 抽样统计

**为什么逐值**：嵌入式的数值缺陷典型形态是「差一点，但一直差」——
除数抄成 3、截断方向反了、边界差一。这类缺陷在**分布上只差一两个百分点**，
抽样统计和眼看都过得去，逐值对账立刻就红。

推荐的覆盖清单（可直接照抄成检查项）：

- **常量**：逐一相等
- **定义域全量**：如果参数是 `uint8_t`，就跑 0..255 全域
  （不只是业务范围 —— 业务外的值顺带验类型边界不回绕）
- **每个分段/等级的边界三点**：`阈值-1 / 阈值 / 阈值+1`
- **溢出邻域**：`0xFFFFFFFF` 一类的极值钉在预期钳制值上
- **锚点**：一两个人工算过的具体值（防止「两边一起错」）

最后一条尤其重要：逐值对账验的是「两边一致」，
**如果两边同源同错，它全绿**。锚点是唯一能挡住这个的东西。

## 第三章 门禁纪律：反向验证与二阶陷阱

### 3.1 恒绿的门禁比没有门禁更坏

一个永远绿的门禁不是「没帮上忙」，是**主动有害**：
它让后面每一轮都误以为这块验过了，从而不再看。

**所以每个新门禁交付时必须做反向验证**：故意改坏被测代码，
确认门禁**退出码非 0**，再改回。

### 3.2 二阶陷阱：验证门禁的手段自己恒绿

这是参考项目实际踩到的，值得单独写（`docs/STATUS.md:382-388`）：

做反向验证时用 `sed` 改坏一个副本，但**`sed` 的模式没命中**
（源码里有个 `(int)` 强转，模式没考虑），副本**实际没被改动**，
于是门禁照常绿。那一刻「绿」被读成「门禁有效」，
而实际上什么都没验 —— **验证门禁的手段自己恒绿了**。

**所以反向验证有两步，顺序不能反**：

```bash
cp mymodule.c /tmp/broken.c
sed -i '' 's/5 \* n \* n \* n \/ 2u/5 * n * n * n \/ 3u/' /tmp/broken.c
# 第一步：断言改坏生效 —— diff 必须非空
diff -q mymodule.c /tmp/broken.c && { echo "改坏未生效，反向验证无意义"; exit 1; }
# 第二步：才看退出码
python3 tools/verify_mymodule.py /tmp/broken.c && { echo "门禁恒绿！"; exit 1; }
echo "反向验证通过：门禁能挂"
```

**这条可以推广**：任何「用改坏来验证检查器」的场合，
都要先断言改坏本身生效。同一个形状在别处也会出现
（改配置验报警、删数据验备份、断网验重试）。

### 3.3 门禁要断言「结果性质」而不是「调了某个函数」

一个反面例子：想保证图像转换做了填充处理，
断言写成「转换脚本里调用了 `flood_fill()`」——
这只证明代码路径存在，不证明**输出对**。函数可能参数错、
可能对某类输入不生效。

**正确的写法是断言输出的性质**：「转换后的图像里，
不该透出背景的区域其像素值不等于背景色」。
这样无论内部怎么实现、怎么重构，门禁验的都是真正在乎的东西。

**判据**：如果被测代码换一种实现方式（同样正确）会让门禁变红，
那门禁断言的就是实现细节而不是结果性质。

## 第四章 观测手段必须能看见故障

**这是整个框架里最重要的一章。** 参考项目的五个历史缺陷
加上两个由用户实测发现的缺陷，**根因全部是同一个形状**：
观测手段绕开了、或者原理上覆盖不到出故障的那个环节。

### 4.1 三种失效形态

**形态一：观测绕开了出错的环节。**
屏幕颜色错乱，但截图一直正常 —— 因为截图取的是**字节序交换之前**的缓冲，
而故障发生在交换之后的 DMA 推屏。截图走的那条路根本不经过故障点。

**形态二：观测扰动了被观测的状态。**
要测「随时间衰减」，而截图靠复位触发，复位又把状态初始化了 ——
每次测到的都是初始值。

**形态三：观测在原理上没有目标故障的分辨力。**
用户报「界面有时先渲染一半再出来」。这类**跨帧中间态**缺陷：
- 截图机制是「按当前状态变量重画一遍」，
  中间态不存在于任何一帧的「状态」里 → 看不见
- 一张 240×320 的截图 base64 后约 200 KiB，传输时间远大于一帧
  → 即便能抓帧也抓不到指定帧
- 宿主门禁没有屏幕 → 看不见
- 串口日志里没有像素 → 看不见

四条通道全部不可见。**不是没跑到，是没有任何通道能反映它。**

### 4.2 判断清单：拿到一个验证手段，怎么判断它能不能看见目标故障

按顺序问这五个问题。**任何一个答不上就说明这个手段对这类故障无效。**

**Q1. 如果目标故障现在就发生，我这个手段的输出会变吗？**
这是核心问题。答案是「不会」→ 观测点选错了（形态一）。
具体做法：找出故障发生的**确切位置**（哪个函数、哪条语句、哪个硬件阶段），
再确认观测取数的位置**在它之后**。

**Q2. 我的观测动作本身会改变被观测的状态吗？**
复位、重新初始化、重画、加锁 —— 这些都可能清掉或改变要测的东西（形态二）。

**Q3. 我的采样率/分辨力够吗？**
故障持续多久？我的采样间隔多长？
一次观测的开销是否大于故障的存在时间（形态三）？
定量算，不要估：帧率、传输字节数、波特率、超时值。

**Q4. 故障的表现形式在我的观测通道里存在吗？**
像素问题不要指望日志（日志里没有像素）；
时序问题不要指望单帧截图；
数值问题不要指望肉眼看屏幕（小图元分辨力不足）。

**Q5. 如果这个手段永远不报警，我怎么知道它是「没问题」还是「坏了」？**
这就是第三章的反向验证。答不上 → 这个手段的绿色没有信息量。

### 4.3 「没测到」与「没发生」必须分开写

报告里这两句话长得像，含义完全不同：

- 「实测未发现冲突」= 我跑了，观测到正常
- 「静态分析未发现阻塞性冲突」= 我没跑，我推的

**写结论时必须标明是哪一种。** 参考项目的做法是每份验证报告
末尾附一张表，逐条标注「我的手段能不能看见这条结论的反例」，
标注三档：**可信 / 量级估计 / 未验证**。

这张表的价值在于：它让「我不知道」变成一个**显式的、可被后续处理的条目**，
而不是被沉默掉。沉默的不确定性会被下一轮当成已验证。

### 4.4 观测能力本身要建设

嵌入式项目应当**主动投资**几条观测通道，它们的收益远超成本：

| 通道 | 做什么 | 关键细节（都是踩出来的） |
|---|---|---|
| 屏幕转储 | 把帧缓冲编码打到串口，PC 侧存成图片 | 取**最接近硬件**的那份数据（字节序交换之后），否则绕开故障 |
| 按键注入 | 从串口读字符合成按键事件 | **绕过按键驱动的时序判定**（双击窗口等），让测试不受时序影响 |
| 状态轨迹 | 关键状态每 N 拍打一行紧凑日志 | 打**帧号**而不只是值，才能验时序 |
| 资源水位 | 堆/DMA 余量定期打日志 | **最大连续块比总量重要**：需要 N 个连续块的分配，总量够但碎片化就失败 |

最后一条的具体例子：某音频外设首次配置要 6 个 480 字节的连续 DMA 块。
只看堆总量永远是「够」，而实际失败是因为拿不到连续块。
**观测项要对着分配方式设计，不是打个总数了事。**

## 第五章 呈现层：把不变量放进编译期

### 5.1 只活在注释里的不变量等于没有

参考项目里有一条注释，写得非常清楚：

> **每个元素都不跨横带边界**（带边界在 y=80/160/240）。
> 跨界的元素会被两条带各画一半，而两条带的重画频率不同 ——
> 上下两半会不同步，屏幕上是撕裂的字。

注释不但写明了不变量，**还写明了违反后的确切症状**。
后来加了一行界面元素，坐标违反了这条，症状与注释描述的一字不差 ——
**由用户发现，不是由验证发现。**

我扫过那个项目 56 个源文件的规范性注释（含「必须/不能/不许/禁止/只能」
一类措辞），命中 **85 条**，其中按「注释里出现可计算实体」分类：

```
prose（需人判）        59
arithmetic（可算）     14
cross-check（可对账）  12
→ 可机械检查 26 条 / 85 条 = 30%，其中真有守护的约 12 条
```

**30% 的规范性注释是可机械检查的，而实际只有一半有守护。**
这个比例在别的项目大概也是这个量级 —— 值得每个项目自己扫一遍。

**推广的结论**：注释是知识，不是守护。
一条不变量若可机械检查，就应该变成断言或门禁；
若不可机械检查，至少要在文档里登记为「靠人守」的显式清单。

### 5.2 编译期断言：违反就构建失败

对**常量坐标**的布局不变量，可以做到编译期挡住。模板：

```c
// screen.h
#define BAND_H 80
#define SCREEN_H 320

// 元素是否完整落在一条带内
#define ELEMENT_FITS_BAND(y, h) \
    ((h) > 0 && (y) >= 0 && (y) + (h) <= SCREEN_H && \
     (y) / BAND_H == ((y) + (h) - 1) / BAND_H)

// 违反则构建失败，运行期零开销
#define ASSERT_WITHIN_BAND(name, y, h) \
    _Static_assert(ELEMENT_FITS_BAND((y), (h)), \
                   #name " crosses a screen band boundary")
```

用法（文件作用域，紧挨坐标定义）：

```c
#define STATUS_Y 12
#define STATUS_H 16
ASSERT_WITHIN_BAND(status_line, STATUS_Y, STATUS_H);
```

**这是原则 B 的直接落地**：能编译期挡住的，绝不留到设备上。
参考项目落了 14 处这样的断言。

**能抓**：所有常量坐标的越界/跨界。
**抓不住**：运行期才确定的坐标（滚动偏移、居中计算）——
那部分要靠 5.3 的静态扫描，或运行期计数器（5.4）。

### 5.3 静态扫描补上宏与循环表达的坐标

编译期断言要求你**手写**每一条。对于「循环里算出来的坐标」
（`y = BASE + i * STEP`）没法逐条写，需要一个静态扫描脚本：
解析 `#define`、函数宏、常量数组、局部变量、`for` 循环域，
对绘制调用的坐标求值并检查不变量。

**这个脚本有三条设计纪律，缺一条就会重犯它要防的错**：

1. **无法静态求值的必须显式报 SKIP 并打印**，绝不静默通过。
   （被检查的那个 bug 的成因就是「越界像素静默丢弃」——
   检查器自己不能犯同一个错。）
2. **退出码只由确定的违规决定**，SKIP 不计入失败。
   否则永远红，然后被人忽略，等于没有。
3. **豁免必须带理由、绑定行号、逐条打印**。
   行号绑定意味着代码一挪豁免就失效 —— 这是有意的。
   **绝不允许为了让门禁变绿而加豁免**，那正是它要防的恒绿。

参考项目的这个脚本当前输出：确定违规 0、豁免 0、SKIP 5（逐条列出表达式）。
它上线时抓到过三处真实违规，其中一处正好是**验收证据本身所在的那行文字**
—— 用来证明功能正确的那行渲染代码自己跨带。

> 这件事值得记：**验收证据可能落在缺陷上而不自知**。
> 截图看不出来，因为转储路径一次性重画全部区域，不存在频率差。

### 5.4 运行期计数器：最小成本的兜底

如果绘制底层对越界坐标是「静默丢弃」，
加一个计数器（调试构建）并在转储时打印出来。

**能抓**：任何越界写。**代价**：几行。
**收益**：上面那个跨带缺陷，如果有这个计数器，
第一次画那个界面就会暴露。

**这条的普适形式**：**任何「静默丢弃」的路径都应该可计数。**
静默丢弃是嵌入式代码里非常常见的防御写法（越界、缓冲满、超时），
它保证了不崩，但也保证了你看不见。计数器是两者的折中。

## 第六章 并发纪律

RTOS 上并发缺陷的特点是**偶发、且症状远离原因**。以下几条是实践里
反复被验证的，每条都给出「不这么做会怎样」。

### 6.1 慢操作绝不留在临界区内

写 flash / EEPROM、网络请求、长循环 —— 这些持锁做，
会让所有等这把锁的任务一起卡住。

**不这么做会怎样**：参考项目里有个状态快照函数，
锁超时 50ms 就走降级分支；而同一把锁的另一处持锁做 flash 写入，
最坏几十毫秒 —— **超时值与最坏持锁时长同量级**，降级分支随时可能触发。

**做法**：临界区内只做内存拷贝（微秒级），慢操作挪到锁外：

```c
// 锁内：拷一份要写的数据
take(state_lock);
memcpy(&buf, &state, sizeof(buf));
give(state_lock);
// 锁外：慢操作
storage_write(&buf);        // 绝不持有 state_lock
```

需要序列化写入本身时，用**第二把锁**，并规定**单向获取顺序**
（如 `save_lock → state_lock`，永不反向）。单向顺序是防死锁的最简办法。

### 6.2 宁可短锁等待，不要超时后偷读

「拿不到锁就读旧值」这种写法很常见，但要看它读的是什么。
如果降级分支读的是**同一份正在被修改的数据**，
那它读到的是撕裂值，不是旧值 —— 而注释往往写着「给上一次的值」。

**判据**：降级分支必须有**独立的影子副本**，否则它不是降级，是数据竞争。

### 6.3 头文件里写明线程契约

模块的头文件应当写清楚：
- 哪些函数可以从哪些任务/上下文调用
- 是否可从中断服务程序调用（会阻塞的一律不可）
- **UI 框架的锁不能替代状态同步** —— 这两件事保护的是不同的东西

**不这么做会怎样**：参考项目里有个状态一致性，
实际是靠 UI 框架的递归锁**间接**保证的（所有读取方恰好都在那把锁下），
而头文件对此一字未提。下一个人起一条新任务、不持那把锁去读，
缺陷立刻从「不可达」变成「可达」。

**这条的普适教训**：**正确性若依赖一个没写下来的前提，
它等于随时会坏。** 把前提写进头文件，或者（更好）
让模块自己保证而不依赖外部锁。

## 第七章 素材与资源管线

针对需要美术/音频/数据表的项目。

### 7.1 同一条管线，单一来源

所有素材（数值表、图像、音频）从**同一个上游来源**取，
走**同一条转换管线**。

**不这么做会怎样**：不同来源的格式差异会以「看起来对但细节错」的形式
出现。参考项目里试过手画一个人物立绘，
失败后改用与其它素材同源的官方素材、走同一条已验证的管线，
一次成功。**手画规则几何体都失败过，人物风险高一个量级。**

### 7.2 同一份数据的多重语义要显式处理

例子：2bpp 图像里的颜色索引 3 在「精灵内部」表示高光（要填充），
在「精灵外部」表示透明（不画）。**同一个数值两种含义。**

不做区分处理（如从边界洪泛填充判定内外），
结果是内部高光透出背景色 —— 参考项目实测某素材的索引 3 占 78.7%，
上屏后整片区域消失。

**普适形式**：**任何「同一编码多重语义」的地方都要显式判定**，
且判定逻辑要有门禁断言输出性质（第三章 3.3）。

### 7.3 转换管线的门禁断言输出，不断言过程

见 3.3。断言「输出图像里该有内容的区域不等于背景色」，
不要断言「调用了填充函数」。

### 7.4 构建时自动同步派生资源

如果某个资源是从源码派生的（例如中文字库要包含源码里所有用到的字形），
**让构建自动同步**，不要靠人记。

**不这么做会怎样**：参考项目缺过一个字形，
因为中文字符串硬写在 C 里，而字库生成脚本看不见它们。
修法是扫源码字面量 + 构建时同步。

## 第八章 多角色协作时的契约纪律

如果开发涉及多个执行者（多人、或多个 AI 代理），以下几条有实测证据支持。

### 8.1 权限只从契约来，消息不授权

一个执行者收到「请改 X 文件」的消息时，如果 X 不在它的写允许清单里，
**正确做法是拒绝并要求更新契约**，而不是照做。

**证据**：参考项目里执行者三次正确拒绝越权
（无目标契约、路径不在白名单、消息试图修改验收标准），
每次都避免了并发写冲突或验收标准被绕过。

### 8.2 一路一个写者

同一文件路径在同一轮里只能有一个写者。并发写同路径是明确禁止的。
这条让「谁改坏的」永远可追。

### 8.3 契约错误由执行者拦下，而这是设计的一部分

**证据**：参考项目的协调者写契约时出过五次实质错误
（语义理解错、编号错、只改一处而漏了同类、归因错、数据类型装不下），
**全部在动手前被执行者或门禁拦下**。

**这说明契约的价值不只是分工，而是「把假设写下来供人反驳」。**
口头交办不会被反驳，因为没有可指着说「这条错了」的东西。

### 8.4 执行者要复核协调者给的前提

不要把上级给的背景当既定事实。参考项目里，
协调者给的「可用堆只有 187 KB」是引用了另一个固件的数字（实际 231 KB），
「某条进度条跨界 1 行」实际是标签也跨且跨 4 行。

**做法**：契约里的关键数字，动手前自己复核一遍并把复核方式写进报告。

## 第九章 成本：这套东西不是免费的

### 9.1 实际投入（参考项目）

| 项目 | 投入 | 说明 |
|---|---|---|
| 纯模块分层 | **前期设计成本** | 要在写第一行逻辑前就决定哪些算「纯」。事后拆分代价高得多 |
| 十一个宿主门禁 | **七轮迭代累积** | 不是一次写完的；每个功能落地时配一个 |
| 单个门禁 | 约 100~400 行 Python + 内嵌 C | 含文档注释；覆盖设计比代码量更费时 |
| 反向验证 | 每个门禁约 10 分钟 | 但**省掉它整个门禁可能白写** |
| 观测通道（屏幕转储 + 按键注入） | 一次性，各约 150 行 | **收益最高的一笔**，之后每轮都在用 |
| 布局静态扫描 | 约 200 行 | 抓到 3 处真实缺陷 |
| 编译期断言 | 每处 1 行 | 几乎免费 |

### 9.2 什么时候不要做

- **不要为「体验够不够好」造门禁。** 那是产品判断，
  自动化它会变成主观规则的堆积，且永远滞后于真实审美。
  参考项目的做法是承认这一条只能靠用户反馈。
- **不要在没有基准时强推逐值对账。** 没有参考实现就没有「应该是什么」。
- **不要为了凑覆盖率给平台层写门禁。** 平台层的价值在设备上验，
  给它写宿主门禁需要大量 mock，而 mock 与真实平台的差异本身就是缺陷来源。

### 9.3 对账门禁的固有上限

**对账门禁的上限是基准的完整度。**

参考项目里有个字段在基准侧只是一个布尔标志、
没有对应素材也没有渲染实现；目标侧照样没实现。
两边一致 → 门禁全绿 → 用户看到功能缺失。
**门禁工作正常，它只是回答不了「基准本身够不够」。**

**对策**（零代码）：给项目建一份「基准缺口」清单，
凡是基准里「有标志位、无实现」的地方都登记为**移植前必须决定做不做**的待决项。
让缺口在动手**之前**变成显式条目。

**配套的机械检查**：死字段检测 —— 找出「有赋值、无读取」的字段。
参考项目扫出两个真死字段（其中一个正是上面那个），
另有一个是有意保留的存档字段，需要白名单机制
（字段旁 `// dead-ok: 理由`，检测器跳过并统计）。

**抓不住**：「被读了但读的结果不影响输出」——
那要数据流分析，代价高一个量级，通常不值得。

## 附录 A 新项目的落地顺序

如果从零开始，建议这个顺序（每步都能独立产生价值）：

1. **先定分层**：哪些模块是纯逻辑（不碰平台头）。写进 `AGENTS.md`/`README`
   作为硬规矩。**这一步最便宜且最不可事后补**。
2. **建两条观测通道**：屏幕/输出转储 + 输入注入。
   它们让后面每一轮验证都能自助完成，不用求人按键或拍照。
3. **第一个纯模块 + 第一个门禁 + 反向验证**。
   走通一遍完整流程，后面的都是照抄。
4. **编译期断言**：把已知的常量类不变量逐条加上。几乎免费。
5. **扫一遍规范性注释**，把可机械检查的那部分列出来，
   按价值排序逐步变成门禁。
6. **资源水位与状态轨迹日志**：在第一次遇到偶发问题之前就加好。
   事后加的成本一样，但事前加能省掉一次「查不到原因」的循环。

## 附录 B 一页速查

**三条原则**：宿主能验的不留到设备；编译期能挡的不留到运行期；
观测手段必须能看见目标故障。

**观测五问**：故障发生时我的输出会变吗 / 观测会扰动状态吗 /
采样率够吗 / 故障形态在我的通道里存在吗 / 它永远不报警时我怎么知道它没坏。

**门禁三律**：反向验证（且先断言改坏生效）；断言结果性质；
无法判定的显式 SKIP 且不影响退出码。

**两句必须分开写**：「没测到」≠「没发生」。
