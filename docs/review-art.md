# 逐页美术缺口盘点

> 方法：读 `docs/pages/P1~P8`、`docs/systems/S16`、`S17`，对照
> `tools/inspector/template.html:828~936` 的 `drawP1~drawP7` 实际渲染代码，
> 以及 `assets/` 六个文件、`sim/pixelart.py`、`sim/effects.py` 的实测。
> 字节数全部用 `(w+3)//4*h`（2bpp 每字节 4 像素）算，不是估的。
> 快照 2026-09-03。

## 0. 一句话结论

**sprite 完全够用，UI 构件全是缺口** —— 151 只 front/back 齐全，
但血条、进度条、判定条、文本框、状态栏分隔线**在原型里 100% 是 canvas 矢量描边**，
这正是 `sim/pixelart.py` 顶部记下的那次教训（矢量圆在像素画里太平滑）复发；
而真正会**让页面不可用**的缺口只有一个，且不是图形而是字库：
**font16.bin 里没有 `A` `B` `C` `[` `]` 五个字形，八个页面的底部三键提示行会渲染成
「照料 图鉴 遭遇」——键名全空白**。

## 2. 五个特别问题

### 2.1 道馆要展示馆主吗？—— **文档从未要求，8 张立绘是伪缺口**

证据三条，都是否定的：

1. `docs/systems/S17-gyms.md` 124 行**通篇没有一个字提到立绘、头像、图标或任何视觉呈现** ——
   全部在讲解锁门槛、等级上限、数据来源。
2. `sim/gyms.py` 21 KB **零图形代码**（grep `sprite|portrait|icon|draw` 零命中），
   它导出的是 `check_gym()` / `level_cap()` / `progress_summary()` —— 纯规则层。
3. **S17 没有对应页面** —— `docs/pages/` 只到 P8，`gen_pages.py` 生成的页面清单里没有道馆页。
   `sim/party.py:262` 提到「P9 队伍页」，但那是 S14 的，也同样没有页面文档。

所以**不是「缺 8 张立绘」，是「缺一个页面设计」**。在页面都还没设计的阶段谈立绘尺寸是本末倒置。

但既然问了，给数字备查（**并非建议做**）：

| 尺寸 | 单张 | ×8 | 占 8MB |
|---|---:|---:|---:|
| 48×56 | 672 B | 5.2 KB | 0.06% |
| 64×72 | 1,152 B | 9.0 KB | 0.11% |
| 80×96 | 1,920 B | 15.0 KB | 0.18% |

**flash 完全不是约束**（现有资产 148 KB = 1.8%，八张立绘再大也是零头）。
真约束是两条别的：
- **没有 8 张馆主的 2bpp 素材来源。** 151 只 sprite 来自 PokeAPI/sprites 仓库（`gray` 变体，
  零有损转换）；馆主立绘 PokeAPI 不提供，得从别处找或手画 —— 手画 8 张 64×72 像素立绘
  是本项目**至今没有过的工作类型**（所有素材都是脚本转换或算法生成的）。
- **画风一致性风险。** `pixelart.py` 的教训是「手画一版 16×16 精灵球，不对称、白格没对齐」
  —— 规则几何体手画都失败了，人物立绘的风险高一个量级。

**建议：不做。** 道馆用「徽章 + 馆主名 + 属性 + 队伍等级」的文字表就够 ——
S17 的信息量本来就是数值型的（门槛进度、等级上限），立绘不承载任何信息。

### 2.2 徽章 8 个：**需要，且能算法生成，128 B**

需要的理由比立绘硬：徽章是**进度的唯一可视化载体**（`progress_summary()` 返回徽章数，
`00-handoff.md:72` 把「徽章进度」列进状态面板）。八枚徽章排一行是玩家「我走到哪了」的答案，
而 S17.1 说的就是「没有任何东西告诉玩家你走到哪了」。

**同一形状 + 8 套调色板完全成立**，因为徽章本来就是颜色名：

```
灰色 / 蓝色 / 橙色 / 彩虹 / 粉红 / 金色 / 深红 / 绿色
```

原版八枚徽章形状各不相同（Boulder 是八角、Cascade 是水滴…），但**本项目的中文名是颜色**
（S17.4 的第一个陷阱就是「徽章是颜色名不是英文概念直译」）—— 既然名字靠颜色区分，
形状就不必区分。这不是偷工，是与命名一致。

| 方案 | 字节 |
|---|---:|
| **16×16 单形状 + 8 套 4 色调色板** | 64 + 8×8 = **128 B** |
| 20×20 单形状 + 8 套调色板 | 100 + 64 = 164 B |
| 24×24 单形状 + 8 套调色板 | 144 + 64 = 208 B |
| （对比）8 张独立 16×16 | 512 B |

**16×16 够用**：徽章是状态指示不是主体，八枚排一行 = 16×8 + 间隙 = 约 160px，塞进 240 宽有余。
生成方式照 `menu_cursor()` 的路子 —— 几何形状（八角星或圆内嵌菱形）算法画，
`poke_ball()` 已经证明「先量化到像素网格再判断」能拿到台阶感。

**「彩虹徽章」是唯一例外**：4 色调色板放不下彩虹。两个出路 ——
用「四色渐变」近似（2bpp 只有 4 级，本来就是这个上限），或给它单独一张 64 B 形状。
建议前者，字节为 0。

### 2.3 `show_oak` 是**死 flag**，博士立绘建议不做

**现状：确实是死的。** `sim/opening.py:78` 定义 `show_oak: bool = True`，7 框里 6 框为 True、
最后一框 False（`:131`）—— 但：

- 项目里**没有任何大木博士素材**（`assets/` 六个文件全部是 sprite/调色板/字库/数据）
- `grep -rn "oak" tools/inspector/` **零命中** —— 验收平台不读这个字段
- 没有任何渲染代码消费它

所以它现在的全部作用是**记录一个意图**：最后一框博士退场，画面留给玩家。
那个意图（第 7 框的「留白」）**用「不画」也能表达 —— 只要前 6 框有东西可画**。

**要立绘的话尺寸算得出来**：240×320 屏，文本框按原版比例占下方 4 行 ×
（16px 字 + 行距）≈ 96~112px，即 Y 208~320；上方 208px 减去标题区，
博士可用高度约 150px，宽度居中约 100px。取 **88×112 = 2,464 B**（0.03% flash）
或 **72×96 = 1,728 B**。

**但建议不做，理由同 2.1**：没有素材来源、手画人物风险高。
**而且开场有一个更好的替代已经写好了** —— 第 ③④ 框有 `show_mon=25`（皮卡丘出场），
那是**现有资产**（`gen1_front.bin` 里的 #25）。开场的视觉主角让皮卡丘承担，
博士只用文字说话 —— 这与 S16「三处审核改动都在文字上」的取向一致：
**S16 是一份文本设计，不是画面设计。**

若最终决定要，处理办法是把 `show_oak` 从 `bool` 改成「文本框上方留多高的空位」的语义，
让它先成为版式字段（有用），再等素材到位变成立绘字段。

### 2.4 back 32×32 vs front 40/48/56 —— **改缩放倍数，不要重导出**

现状比例（`drawP3:859-860`）：

| front 档 | @scale2 | back @scale1 | 比例 |
|---|---:|---:|---:|
| 40×40 | 80px | 32px | **2.50×** |
| 48×48 | 96px | 32px | **3.00×** |
| 56×56 | 112px | 32px | **3.50×** |

野怪比自机大三倍，观感上「我派了只幼崽去打巨兽」。

**方案 A（推荐）：back @scale2 = 64px，front 保持 @scale2 = 80~112px → 比例 1.25~1.75×**

- 字节成本 **0**
- 1.25~1.75× 是**合理的**：原版 GB 的 back 就比 front 大（自机在前景），
  这里反过来但幅度温和 —— 野怪在远处稍大一点，透视上说得通
- 整数倍缩放，C3 无 FPU 也没问题（`effects.py` 用整数分数就是为这个）
- P1/P5 的 back @scale3 = 96px 不受影响（那两页 back 独占画面）

**方案 B：重导出 back 到 48×48 —— 不建议**

| 目标 | 151 只总字节 | 相对现有 38.7 KB |
|---|---:|---:|
| 40×40 | 59.0 KB | +20.3 KB |
| 48×48 | 84.9 KB | **+46.2 KB** |
| 56×56 | 115.6 KB | +76.9 KB |

flash 装得下（+46 KB 只占 0.55%），但**源头不支持**：
`tools/pipeline/convert_gen1.py:162` 写 `BACK_SIZE = 32  # back 实测 151 只全部统一 32×32`，
`build_back_atlas()` 对非 32×32 直接抛 `意外尺寸`。
PokeAPI/sprites 的 RBY back 原生就是 32×32 —— **放大到 48 只能插值，那是有损的**，
而项目引以为豪的是「用 `gray` 变体转换零有损」。放大后的软边会重演矢量圆那次的画风打架。

**结论：改 `sprAt` 的 scale 参数，一行代码，零字节，零有损。**

| 指针三角（P4） | `beginPath/moveTo/lineTo/fill` **贝塞尔路径同族** | `:877-878` | ⚠️ **矢量路径** |

| 状态栏分隔线 | `strokeStyle + moveTo/lineTo` | 每页第 2~3 行 | ⚠️ 矢量，但 1px 直线**填色即可**，不算风险 |
| 菜单选中光标 | `txt(ctx,"▸")` —— **字库里没有 ▸** | P2/P5/P6/P7 | ✅ **`pixelart.MENU_CURSOR` 已备好，18 B，未接线** |

**`fr()`（`strokeRect`）是主要问题**：它给每条进度条画一个 1px 平滑矩形描边。
矩形描边比圆好一些（直线没有反锯齿），但 `strokeRect(x+.5,y+.5,...)` 的半像素偏移
在缩放显示时会产生灰边 —— 那正是「没有台阶感」的来源。

**修法是零字节的**：条框改成「按像素填色」的点阵框（四条边直接写像素，
拐角单独处理），而不是调 canvas 的描边 API。给出点阵条框的字节估算是为了完整性 ——
若做成可复用素材：

| 构件 | 尺寸 | 字节 |
|---|---|---:|
| 进度条框（左端帽 + 可平铺中段 + 右端帽） | 4×10 + 4×10 + 4×10 | ~30 B |
| 判定条框（200×18，同法三段） | 4×18 ×3 | ~48 B |
| 朝下指针三角 | 9×5 | ~12 B |
| 角标底框 | 12×12 | ~36 B |
| **小计** | | **~126 B** |

但更可能的实现是**代码画像素而不存素材**（跟 `menu_cursor()` 一样算法生成）→ **0 B**。

## 3. 意外发现：字库缺 5 个字形，八个页面的三键提示行会残缺

这不在任务清单上，但它比任何图形缺口都严重，所以单列。

**实测**：`assets/font16.bin` 545 个字形，逐字节解出码点表后核对 ——
`A` `B` `C` `[` `]` **全部不在字库**（`L` `v` `H` `P` `#` `♥` 也不在）。

而八个页面文档每一份都写着底部提示行是：

```
[A]照料 [B]图鉴 [C]遭遇      184px / 232px（余 48px）
```

**这行文字上屏时会变成「照料 图鉴 遭遇」—— 键名全部渲染成空白**，
玩家看不出哪个动作对哪个键。三键设备上这等于八个页面都不可用。

根因：`tools/pipeline/convert_font.py:174-175` 的固定符号集是
`set("0123456789/×★☆%·—")` —— **只有数字和符号，没有拉丁字母**。
而 `sim/strings.py:33` 的注释明确写了提示行格式含方括号与键名，
`KEYS` 字典的键就是 `"A"/"B"/"C"` —— 但 `strings.charset()` 只遍历 `all_strings()`
（136 条文案，全中文），**从不遍历 `KEYS` 的键**。所以 `[`、`A` 从来没进过字符集。

这与 `convert_font.py:135-145` 记录的前两轮缺陷是**同一类**（S17 漏 29 字、
S14/S18 漏 16 字），且表现相同（真机上渲染成空白）——
但那两轮是「模块没登记」，这一轮是「登记了的模块自己漏了一部分」。

**修法（160 B）**：`ui_chars |= set("ABC[]")`，或更彻底地在 `strings.charset()` 里
`for page,keys in KEYS.items(): out |= set(keys.keys())`。后者能防止将来加第四个键时再漏。

**顺带一个数值问题**：`strings.text_px()` 按「ASCII 半宽 8px」算，
得出提示行 184px。但 `font16.bin` 是**定长 16×16 每字形 32 字节**，
`per = size * ((size+7)//8) = 32`，**没有半宽机制**。
实测数字字形的墨迹范围是 x=4~11（8px 宽的字画在 16px 格子里居中）——
即字形本身是半宽的，但**存储与步进都是全宽 16px**。

若固件按字形宽度 16px 步进，提示行实际是 **17 字 × 16 = 272px > 232px 可用宽，溢出 40px**。
八份页面文档写的「184px / 232px（余 48px）」建立在半宽步进的前提上，
而那个前提**在字库格式里没有对应实现**。这不是渲染 bug 而是规格缺口：
要么固件对 ASCII 做 8px 步进（需要知道哪些字形是半宽的 —— 字库里没存这个标记），
要么排版按 272px 重算（放不下，得改文案）。

建议连带处理：字库头部或索引加一位「半宽」标记（545 字形 × 1 bit = 69 B），
让 `text_px()` 的假设有依据。

## 6. 三句话总结

1. **sprite 层完全够用，一张都不缺** —— 151 只 front（40/48/56 三档）+ back（32×32）
   + 20 套调色板，无空洞；P3 的比例失配改一个 scale 参数就解决，零字节零有损。
2. **UI 构件层全是缺口，但全部零字节可修** —— 血条/判定条/指针/选中光标现在是
   canvas 矢量描边或不存在的字库字符；`pixelart.py` 已备好 363 B 素材，
   `effects.py`+`transitions.py` 已备好全部动效，**一个都没接线**。
3. **唯一会让页面不可用的缺口不是图形而是字库的 5 个字形（160 B）** ——
   `A B C [ ]` 缺失使八个页面的三键提示行键名渲染成空白；
   而立绘那两项（8 张馆主 + 博士）是伪缺口，文档从未要求，建议不做。
