## 6.1 存档鲁棒性（必需项，不是过度设计）

这类设备随时会被拔电或耗尽电量。

**养成线一旦引入，存档里就不只是图鉴收集度，而是一只养了几周、有亲密度和成长史的主宠
—— 这是这个项目里唯一不可再生的数据。**

存档写坏等于数周进度归零。因此需要：

- **双 buffer** —— 交替写入 A/B 两份，写完才切换有效标记
- **CRC 校验** —— 启动时校验，坏了就回退到另一份
- **磨损均衡** —— 见下节的写入频率控制

## 6.2 flash 写入频率

连续几周每 30 秒扫一次，若每次都写 flash，磨损会很难看。

策略（详见 [02-sensing.md](02-sensing.md#flash-磨损)）：

- 工作集放 **RTC slow memory**（C3 有 8KB，深睡不丢）
- 512 字节的地点表放 RTC RAM 刚好
- **只在状态转换时与每小时提交 flash**

## 6.3 仿真器：当前阶段的核心工具

这本是本章列出的工作项，但它恰好完全不需要目标硬件 ——
**用笔记本电脑扫 WiFi 就能产出格式相同的数据。**

工作流：

```
采集（macOS/Swift）  →  NDJSON  →  回放器（Python）  →  算法验证
tools/collector/        data/raw/    sim/replay.py       sim/sensing.py
                                     sim/prototype.py    sim/gameplay.py
```

硬件到手时，固件只需替换数据来源，**算法已经在真实数据上验证过了**。

更重要的是，这批电脑采集的数据能**提前回答两个 Phase 0 问题**：
真实环境 AP 密度、以及三态判别的可分性。

虽然电脑的天线和口袋里的设备不同
（[2.6 的标定问题](02-sensing.md#26-口袋标定一个会坑人的实测陷阱)依然存在），
但「家和公司能不能分开」这个**定性结论可以提前拿到**。

### 数据格式

采集与回放之间的契约是 NDJSON，每行一次扫描：

```json
{"ts": 1756800000, "aps": [{"b": "aa:bb:cc:dd:ee:ff", "s": "MyWiFi", "r": -45, "c": 6, "a": "wpa2"}]}
```

字段名刻意压到一个字母 —— 将来固件侧若要落盘同格式，
每字节都要算（[8MB flash 预算](01-constitution.md#11-硬约束清单)）。

| 字段 | 含义 |
|---|---|
| `ts` | Unix 时间戳（秒） |
| `b` | BSSID |
| `s` | SSID（隐藏则为空字符串） |
| `r` | RSSI（dBm） |
| `c` | channel |
| `a` | authmode |

## 6.4 内容管线

需要做的转换（全部在 PC 上，见 [05-art-audio.md](05-art-audio.md#tuxemon-的-411-个-yaml-是最大的现成资产)）：

1. Tuxemon 的 411 个怪物 YAML → 紧凑二进制表
2. DawnLike / Tuxemon 精灵图 → 2bpp 四阶灰
3. 中文点阵字体子集化（只保留用到的字）
4. 按 8MB flash 预算做容量核算

**容量核算已完成，结论是余量充裕**：全部素材只占 17.8%，剩 6.6MB。

早先担心「中文字体和几百张精灵图很容易吃掉大半」——**这个判断是错的**。
实测 12×12 中文全字库（6700 字）只要 117KB，那个估计是按矢量字体或 16×16 算的。

| 项 | 实测 |
|---|---|
| 怪物数据 411 条 | 12.9 KB |
| 精灵图 413 张 @48×48 2bpp | 231 KB |
| 中文点阵 12×12 全字库 | 118 KB |
| 固件本体（估） | 1200 KB |
| **合计** | **约 1.5 MB / 8 MB** |

因此精灵尺寸可以往大取 —— 48×48 只占 2.8%，上到 64×64（411KB）也毫无压力。
详见 [tools/pipeline/README.md](../tools/pipeline/README.md)。
