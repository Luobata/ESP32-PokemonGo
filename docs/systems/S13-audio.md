# S13 音频

当前固件与 Web 同源预览使用 C 音序器：`music.c`、`sound_mixer.c`、`music_director.c`。原有 `sim/audio.py` 及旧 inspector 音效 tab 保留作历史对照。网页 `firmware.html` 的「开启试听」才会创建 AudioContext；默认不播放，后台、暂停、熄屏会停止排队音频。硬件现改用下述持久化运行时开关，默认保持静音。

## 硬件静音开关（2026-09-08 追加）

「菜单 → 选项 → 静音」按 A 切换，控制游戏背景音乐和音效。默认“开”（静音）；使用独立 NVS `pokewalk:mute` 键保存，未保存、读取失败或非法值均按静音处理。写入/提交成功后才改变当前状态，失败显示“保存失败 按A重试”。游戏 V7 结构未改变，队伍、背包和挑战进度不受此偏好影响。

当前固件关闭编译期 `CONFIG_POKEWALK_SILENT_BOOT`，但保留该硬性锁定选项供特殊构建。运行时静音由 `audio_settings.c` 控制，启动先关闭 ES8311，再读取偏好。静音时音频任务不创建/open codec；取消静音后才惰性初始化；静音/熄屏后关闭 codec 并清掉过期音效，唤醒遵守静音偏好。不能把关闭编译期硬锁理解成默认开声。

网页中需要同时开启浏览器「试听」并关闭游戏内「静音」才能听到声音。预览偏好仅存在于该场景会话；硬件偏好重启后保留。此次硬件验证保留静音，切换有声输出与重启持久性在生产 C 配合模拟硬件/NVS 的测试中验证，没有现场播放声音。

| 进化 | evolution |

导入 15 首原音序的音符顺序、声部循环、占空比和定点帧时长，来源固定于 [pret/pokecrystal 7a7881d](https://github.com/pret/pokecrystal/tree/7a7881d0d62e0ddbd82dcf10e7116807487ac651/audio/music)，逐文件哈希见 `assets/music_sources.json`。这不是逐周期 Game Boy APU 模拟：波表声部用三角波，鼓用合成噪声；颤音、滑音和寄存器微调暂未精确还原。不可把当前音色称为与原作录音 1:1。

原有 11 个反馈音效继续使用 C 音序。新增按 15 属性着色的技能命中/落空音效，在命中演出帧触发，属于项目设计而非原版 SFX 脚本移植。混音时背景降至 1/3，切歌淡入约 93ms，末端约 18Hz 去直流滤波；输出 22050Hz 单声道 PCM16。网页只传输 C 混音器的数据，不另写一份 JS 合成器。连续输出不会推进游戏 RNG 或逻辑时钟。

战斗帧间隔由 60ms 延长至 90ms；野战两招间额外留 450ms，训练家招式后留 720ms。音乐按真实音序时长运行，不跟随战斗变慢。

离线验证覆盖每曲 130 秒、分块一致性、循环、叠加、全部属性效果、浏览器默认静音/隐藏/会话切换；硬件扬声器音色、音量和实时负载仍待开启声音后实听实测。以下 CPU 数字与波形讨论来自旧模拟器，不代表新增 C 音序器已完成真机性能测量。

## 13.1 为什么是实时合成

本设备通过 I2S 与 ES8311 输出音频。这里选择由 CPU 实时合成音序，而不把长曲目存成 PCM 文件。

而这恰好是好事：

| | 音序数据 | 16bit PCM |
|---|---|---|
| 11 条音效 | **164 B** | 150 KB |

省 **938 倍**。「几乎不占 flash」不是修辞。

## 13.2 CPU 预算：不是瓶颈

| 采样率 | 每样本周期 | 4 通道占用 |
|---|---|---|
| 8000 Hz | 20000 | 0.60% |
| 16000 Hz | 10000 | 1.20% |
| **22050 Hz** | **7256** | **1.65%** ← 采用 |
| 44100 Hz | 3628 | 3.31% |

算清这个之后才敢照 GB APU 的真实结构做**四个通道**，而不是砍成一两个。
**瓶颈从来不在合成，在中断延迟与 DMA 缓冲** —— 那部分要真机才能测。

22050 而非 44100：听感差异在小扬声器上基本听不出，但 DMA 缓冲省一半。

## 13.3 四通道照 GB DMG

| 通道 | GB 原型 | 本项目用途 |
|---|---|---|
| CH1 | 方波 + 扫频 | 主旋律；扫频用于投球音、进化音 |
| CH2 | 方波 | 和声 / 副旋律 |
| CH3 | 波表（32×4bit） | 低音线；三角波表比方波"圆"，不抢主旋律 |
| CH4 | 噪声（15 位 LFSR） | 打击、失败音 |

包络只有「线性升/降 + 步长」，**没有 ADSR** —— 照 GB 硬件做。
这不是偷懒：GB 音效那种「啪」的干脆感就来自没有 attack 斜坡。

## 13.4 方波必须去直流

朴素方波（高=+1 / 低=−1）在占空比 ≠ 50% 时带直流分量：

```
占空比 0.125 → 直流 −0.750
占空比 0.250 → 直流 −0.500
占空比 0.750 → 直流 +0.500
```

实测闪光音效（全用 12.5%）直流偏移到 **−0.1365**。后果是扬声器持续偏压、
发热、并白吃掉动态余量。

真机上通常有耦合电容滤掉直流 —— 但**不能假设那个电容存在**，
这台设备的音频通路（PWM 还是 I2S）还没确认。在合成侧解决更稳：
输出减去自身直流分量，再按峰值归一化保持 ±1 动态范围。

修完后全部 11 条直流都 < 0.01（最大 `ball_throw` +0.0086）。

## 13.5 混音：只在越界时缩

两个陷阱都踩过：

1. **只在最后 clamp 是硬削波** —— 产生刺耳高次谐波，小扬声器上尤其难听。
   实测 `escaped` 峰值 0.330、`evolve` 0.374 都越过了 `MASTER_VOL` 预算。
2. **无条件按峰值归一化会抹掉音效之间的音量差** ——
   `menu` 峰值刻意压低（它会被按几万次），归一化会把它拉到和 `caught` 一样响。

所以：只在越界时缩，不在未越界时放。

## 13.6 音量梯度与触发频率成反比

| 音效 | RMS | 触发频率 |
|---|---|---|
| menu | 0.042 | 几万次 |
| shiny | 0.079 | 一个存档几次 |
| care | 0.121 | 一天三次 |
| caught | 0.182 | 每天几次 |
| evolve | 0.224 | 一个存档几次 |

常触发的轻、罕见的响。这条比"好听"更重要 ——
一个响亮的光标音听三万次会让人关掉声音。

### 闪光音效为什么偏轻

12.5% 占空比归一化后 RMS 只有 0.378（尖锐音色的固有性质：峰值满，
但大部分时间在低电平）。修法是**提 vol 而不是改占空比** ——
改占空比就换了音色，那份「一听就知道是它」的辨识度就没了。

## 13.7 每条音效的设计

| 音效 | 字节 | 时长 | 设计要点 |
|---|---|---|---|
| `boot_1` / `boot_2` | 6+6 | 90/420ms | 两声的关系是 [S11](S11-intro.md) 开场的灵魂：第一声吊起来，第二声落下去 |
| `encounter` | 14 | 240ms | 三连上行 —— 「有东西出现」 |
| `ball_throw` | 16 | 190ms | 扫频下行（球飞出去）+ 噪声（撞击） |
| `caught` | 18 | 430ms | 上行大三和弦分解，给一个「成了」 |
| `escaped` | 20 | 300ms | 下行两音，**不刺耳** —— 失败音听几百次会烦 |
| `shiny` | 38 | 432ms | 全游戏最该被记住的 400ms。高频交替 + 独立音区 |
| `evolve` | 12 | 900ms | 长扫频上行 —— GB 进化那种「越来越紧张」全在扫频上 |
| `level_up` | 18 | 325ms | 短上行四音，比捕获音轻（出现更频繁） |
| `care` | 10 | 140ms | 最常触发，必须不烦：50% 占空比最圆、时长最短 |
| `menu` | 6 | 24ms | 极短。要「轻」靠时长，不靠音量小到听不见 |

音效普遍在 100~400ms —— 会话是 30 秒量级，800ms 的音效会占掉 2.7%
且要重复听几百次。GB 的音效大多也在这个区间。

## 13.8 一致性检验

验收面板用 **WebAudio 现场合成**，不是播预渲染的 WAV。
JS 重实现同一套公式，与 Python 实测的 peak/dc/rms/样本数逐条比对，
当前 **11/11 一致**。

这说明这套公式换一门语言重写也能得到同样的声音 ——
固件的定点版本（Q16.16 相位累加器代替浮点）有了可比对的基准。

塞 WAV 进页面要 150 KB，且验收不了这一点。

## 13.9 待真机验证

| 项 | 为什么现在测不了 |
|---|---|
| **音频通路是 PWM 还是 I2S** | 规格表只写「扬声器」，没写驱动方式 |
| **是否有耦合电容** | 决定去直流是必需还是保险 |
| 中断延迟与 DMA 缓冲深度 | 真正的瓶颈所在 |
| 实际音量与音色 | 小扬声器的频响曲线未知，低音可能整体听不见 |
| 播放对续航的影响 | PWM 常开会显著增加功耗 |

**背景音乐（BGM）暂不做**：需要先知道续航代价。
音效是事件驱动的（几百毫秒），BGM 是持续的 —— 两者的功耗量级完全不同。

## 2026-09-08：音量与遇敌提示

硬件「菜单 → 选项 → 音量」提供 0–100%，每次 5% 的调节。A 加大、B 减小、C 完成；边界停止，不循环。独立 NVS `volume` 键默认 55，和 `mute` 分别保存，写失败保持原值。调整音量不会解除静音。

声音任务在播放期间更新 ES8311 输出音量；浏览器按百分比缩放 PCM 近似试听，不能据此判断两种扬声器的绝对响度。

新遭遇成功加入队列后发出通知，读档、页面重绘和没有新遭遇的扫描不会重复提醒。普通遭遇用短上行音，稀有度 4–5 使用新编的四音琶音，闪光使用闪光音。并发通知合并，闪光优先于稀有、稀有优先于普通；正在播的招式结束后再播提示。

熄屏不播放背景音乐，但允许短暂打开音频设备播放遇敌提示，结束即关闭；屏幕不点亮。静音时不保留待播通知，解静音后不会补播旧提醒。
