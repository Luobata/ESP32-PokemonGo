# S2 捕获判定

把一次遭遇结算成「捕到 / 没捕到」，用**时机判定 + 球种选择**两层决策撑起 5 秒内的交互。

## 输入 / 输出

| 方向 | 来源 / 目标 | 字段 |
|---|---|---|
| 入 | S1 待处理记录或 world 活动遭遇 | `species_id`、`rarity`、UID 与遭遇时间 |
| 入 | `assets/gen1.bin` 记录 | `capture_rate`（offset 6，原版数值：皮卡丘 190、超梦 3） |
| 入 | `sim/gameplay.py` 的 `PetState` | `catch_window_bonus` —— 心情直接乘窗口宽度 |
| 入 | S3 战斗结果 | 野怪剩余 HP 比例 → 窗口加宽 |
| 入 | S9 道具 | 球种与库存 |
| 出 | S5 图鉴 | 置「已捕」位 |
| 出 | S9 道具 | 扣球（无论成败） |
| 出 | world 遭遇生命周期 | 首次投球前移出待处理队列；成功或逃跑则结束活动目标 |

## 核心逻辑

**第一层：时机判定。** 指针在 200px 宽的条上以 1.2 秒一个往复来回移动，
按 A 键时判断指针是否落在窗口内。

基础窗口宽度为 `capture_rate × 0.55`，各乘数连乘后才做一次四舍五入：

| capture_rate | 基础窗口 | 例 |
|---|---|---|
| 190 | 104.5 px | 皮卡丘 |
| 45 | 24.75 px | 妙蛙种子 |
| 3 | 1.65 px（最终至少 3 px） | 超梦 |

实际窗口 = 基础窗口 × `PetState.catch_window_bonus` × 球种系数 × 战斗加成。
`catch_window_bonus` 的定义已在 `sim/gameplay.py`：`1.0 + (mood - 50) / 100`，
即心情 100 给 1.5 倍、心情 0 给 0.5 倍 —— **这是「养成反哺探索」的唯一落点**
（[04-gameplay.md#433](../04-gameplay.md#433-养成如何反哺探索)）。

**第二层：球种选择。** B 键循环切换：

| 球种 | 系数 |
|---|---|
| 精灵球 | ×1.0 |
| 超级球 | ×1.5 |
| 高级球 | ×2.0 |

窗口宽度最终 clamp 到 `[3, 200]`，判定含窗口两端。达到 200px 时允许必中。

**失败后果（2026-09-08）**：战斗结束前的选择阶段投球失败，回到同一场，由野怪反击一次。
主宠未战败时，反击完成后重新选择 A 捕获 / B 战斗 / C 返回，不会自动接着打完整场。
只有明确按 B 才连续自动战斗，连续期间不能捕获或离开。
双方 HP、下一行动方、已执行攻击数与 RNG 保留；野怪反击可能落空或无效，按原有命中/属性规则处理。
战斗获胜后只有一次实际投球机会，失败立即按 UID 清理活动目标。成功走原子收容/图鉴/结束遭遇路径。
新流程不再随机决定逃跑。`cap_attempt` 与 sim 的旧 `fled` 字段仅保留给底层算法兼容对账，
P4 的实际后果由战斗会话决定。

**动效复用**：命中瞬间用 `sim/effects.py` 的 `flash_sequence()`，
失败抖动用 `shake_sequence()`。闪光**不在这里判定** ——
[S8](S8-shiny.md) 在遭遇生成时就定了，S2 只负责在捕获成功时
把 `is_shiny` 位从同一遭遇记录搬进 S5 的 `dex_shiny_caught` 位图。

## 数据结构

会话通过 `world_battle_get_uid/set_uid` 绑定 UID + 遭遇时间。
`started` 表示已开始处理，包括首次投球；`auto_battle` 仅由明确选择 B 启动。
`retaliation_pending` 在失败切页前写入；`capture_used_after_win` 在最终投球判定前写入。

待处理队列最多 5 条，满后无条件淘汰第一条，新记录追加到末尾。首次实际投球或选择战斗，
world 先持久化移除待处理记录，再发布单个活动目标；保存失败不扣球、不执行攻击，可重试。
活动目标不占 5 条名额，后台 FIFO 不能淘汰它。P3/P4 间切换保留会话，离开这个流程就清理目标，
不能再从列表重进。成功后立即保存收容、图鉴与剩余队列。

当前球库存仍是页面运行期初值 12/3/1，尚未接 S9；完整战斗会话、活动目标与球库存不跨重启恢复。
首次处理前已保存待处理移除，因此重启不会让打过或投过球的目标重新出现。V5 的物理存储布局不变。

## 与三键约束的关系

对应 **P4 捕获页**：**A 投球 / B 换球 / C 取消并回到原战斗**。
投球后所有按键只加速结果停留的唯一出口，不能换球重投。未投球取消不消耗战胜后的唯一机会。

指针往复 1.2 秒 = 屏幕刷新压力可控（条宽 200px，只需重绘指针所在的那一条横带，
符合[分块渲染约束](../01-constitution.md#11-硬约束清单)）。整个交互
按键次数是 1~3 次，5 秒内结束，符合 30 秒会话预算。

## 待 Phase 0 验证的参数

| 参数 | 当前值 | 依赖 |
|---|---|---|
| 指针往复周期 | 1.2 s | 实机 SPI 刷新率。若指针重绘跟不上，周期要放长 |
| capture_rate → 窗口的映射曲线 | ×0.55 后乘心情、球种和 HP 加成 | PC 端手感调参（不需要硬件） |
| 窗口 clamp 上下界 | [3, 200] px | 同上 |

窗口映射曲线可以在 `sim/` 里先调，失败路由以实际 C 页面流程为准。
08-systems.md 把 S2 标为「不依赖实测」是就**硬件**而言 —— 手感仍需调参。

## 边界情况

1. **当前球库存为 0**：显示“没有球了”，不投球、不消费战胜机会，可 B 换球或 C 返回。
2. **未投球取消**：回 P3 的选择或胜利结果阶段，保留当前 HP 和未用机会，不启动自动战斗。尚未处理的目标仍在队列；已处理目标离开 P3/P4 后不回队列。
3. **反击致败**：主宠 HP 归零后结算本场；不能再进捕获，也不能返回后重领经验。
4. **达到 200px 窗口**：所有合法指针位置命中，这是当前难度公式允许的结果。
5. **尚未处理的遭遇被后台淘汰**：按 UID + 时间读取/提交失败后回列表，不把捕获登记到其他条目；活动目标不受后台刷新影响。
6. **设备重启**：活动目标、完整 HP/RNG、待反击和最终机会不恢复；已处理目标不回队列，成功捕获由关键事件存档保护。
7. **首次投球保存失败**：待处理记录与原会话保持不变，球和胜后机会都不消费；重试成功后才投球。

## 验证

`python3 tools/pipeline/verify_capture_flow.py --negative` 驱动真实 P2/P3/P4、时钟与输入，
检查单次反击后返回选择、连续战斗输入锁、取消、单次机会、活动目标清理、收容、图鉴和 EXP，
并逐步比较 dirty/full 像素；私有源码突变必须被门禁拒绝。
`verify_encounter_lifecycle.py --sanitize` 验证实际 world/save 的首次处理保存事务、FIFO、活动槽及并发扫描；
`verify_encounter_lifecycle_preview.py` 验证实际页面切换和按键链路。
