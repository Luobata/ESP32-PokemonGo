# S19 全流程编排

把 19 个系统串成一局游戏。实现见
[`sim/orchestrate.py`](../../sim/orchestrate.py)。

## 19.1 为什么需要它

盘点模块引用关系发现：**8 个模块从未被任何代码调用过** ——
`systems` / `state` / `gyms` / `autosave` / `intro` / `opening` /
`transitions` / `audio` 全是孤岛。它们只被验收平台的 `build.py`
读参数，从没在一次运行里协同过。

`prototype.py` 是唯一的「跑一局」入口，但只串了
`gameplay` + `sensing` + `naming` 三个。

后果不是「代码不整洁」，而是**系统之间的接缝从未被走过**：
时序错了、状态不一致、事件漏派，这些只有真的跑一遍才会暴露。

## 19.2 它做什么

```
① 开场：GB 启动动画 → 博士台词 → 选伙伴 → 建档
② 循环：喂扫描数据 → 感知 → 遭遇 → 战斗/捕获 → 收容 → 存档
③ 长线：徽章解锁判定、进化检查、日切结算
④ 收尾：关机存档
```

一句话跑通：

```python
from sensing import load_ndjson
import orchestrate as O
scans = load_ndjson("data/raw/office.ndjson")
s = O.play_through(scans, choice=3)      # choice=3 → 皮卡丘
print(O.summary(s))
```

## 19.3 设计取向：编排层不含规则

它只负责**调用顺序**与**事件派发**；所有判定仍在各自系统里。

这样固件移植时可以照抄这个顺序，而不用重新推导
「先算掉落还是先收容」这类问题（那个顺序在
[S14](S14-party.md#146-resolve_capture唯一的收容入口) 里有讲究）。

每个改变状态的动作都调 `Session.fire(event)` 派发 autosave 事件 ——
那是 [S18](S18-autosave.md) 唯一的接入点，**不派事件的系统就等于不存档**。

## 19.4 `snapshot()` 里 party[0] 是权威

`SaveData.pet_*` 只是 `party[0]` 的镜像 + 三条轴。
每次快照都从 `party[0]` 重新取，避免两者漂移 ——
那是 [S14](S14-party.md#143-主宠--party0) 明确警告过的 bug 来源。

## 19.5 一跑就抓出四个缺陷

这一节是这个模块存在价值的证据。四个缺陷**单看各自系统的代码都是自洽的**：

### ① `SensingResult` 没有 `biome`

感知层只管「这是哪」（地点指纹），不管「这是什么地方」（biome）。
`biome` 要自己调 `classify_biome(aps)` 算。第一行代码就撞上这个假设。

### ② 道馆门槛按平均分配，真实分布极度不均

跑真实数据（1061 次扫描 / 19.9 小时）算出的分布：

| biome | 占比 | 速率 |
|---|---|---|
| 办公区 | 70.3% | 6.2 h/天 |
| 野外 | 14.5% | 1.3 h/天 |
| 住宅区 | 14.3% | 1.3 h/天 |
| 商业区 | 0.8% | 0.1 h/天 |
| 交通枢纽 | **0%** | — |

原设计每个 biome 平均分配门槛 → 第 6 馆（交通枢纽 34h）需 **3400 天**。

修法的第二层是关键：**稀有 biome 改用「访问次数」而非「累计小时」** ——
偶尔去一次商场是正常的，在那儿累计几十小时不是。这不是调数值，是换衡量方式。

### ③ `classify_biome` 缺 AP 下限保护

加了访问计数后一天能刷出「野外 103 次访问」，而实际驻留只有 0.9h。

追下去：1061 次扫描产生 222 个连续段，**66% 只持续 1 次扫描**。
试了连续计数与滑动窗口多数表决都不行 —— 问题不在计数方式。

根因：**纯办公环境里 17% 的扫描被判成野外**，那些扫描的 AP 数中位是 2
（判对的是 8）。同一间办公室偶尔只抓到两个 AP，就被按「AP 少 = 野外」判了。

这与感知层的 `MIN_APS_FOR_DISTANCE = 5` 是同一个问题 ——
**稀疏扫描不可信**。`sensing.py` 早有防护，`classify_biome` 一直没有。

修完误判 **17% → 0%**，biome 切换从 222 次降到 2 次
（这一天确实只去了两个地方）。

### ④ 交通枢纽是死代码

它要 `ble_count > 10`，但采集工具从不输出 BLE 计数、**5 处调用全不传** ——
自项目开始至今一次都没执行过。而 S17 第 6 馆绑的就是它。

试过找纯 WiFi 替代判据，两个都反了：

```
运营商 AP 占比   家 0.27 > 通勤 0.00
open 网络占比    办公 0.33 > 通勤 0.23
```

地铁站的 AP 密度高、SSID 聚合高，特征与写字楼几乎相同。

## 19.6 biome 访问计数要看持续性

不能简单地「biome 变了就 +1」（见 ③）。
连续 `VISIT_MIN_SCANS = 10` 次扫描判为同一 biome 才算一次访问 ——
10 次 × 30 秒 ≈ 5 分钟。

阈值太低（≤4）会把抖动算进来；太高（≥20）会漏掉真实的短途访问。

`classify_biome` 返回 `BIOME_UNKNOWN`（AP 太少）时沿用上次结果 ——
那是它的契约：**宁可说「不知道」也不猜**。
