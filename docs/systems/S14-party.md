# S14 队伍与仓库

捕到的宝可梦存在哪、怎么切换。实现见 [`sim/party.py`](../../sim/party.py)。

## 14.1 它补的是一个真断层

在它之前，[`attempt_capture()`](S2-capture.md) 成功后只调
`dex.mark_caught()` 点亮一个图鉴 bit —— **那只宝可梦的实体直接消失了**。

存档里只有 `pet_*` 一只主宠，养成、进化、战斗全都只认它。
玩家抓三十只，能玩的还是开场那只：**捕获这个玩法的产出无处可去**。

S1~S13 各自成立，但「捕获 → 养成」这条链是断的。

## 14.2 结构：队伍 6 + 仓库 30

| | 容量 | 依据 |
|---|---|---|
| 队伍 | 6 | 与原版一致 |
| 仓库 | 30 | **三键 UI 的约束** |

仓库 30 不是存储的约束：每只 8 B，30 只才 240 B，8MB 里是零头。
是 UI 的约束 —— B 键循环浏览 30 只平均要按 15 次，
再多就得做分页，而分页要第四个键。

## 14.3 主宠 = `party[0]`

不设独立的 `pet_species` 字段。

「换主宠」等于「把某只移到队首」，一个操作解决两件事，
且**不会出现「主宠与队伍不一致」这种状态** —— 那是上一版结构必然的
bug 来源。

移动用 `insert(0, pop(i))` 而非 swap：swap 会打乱队伍其余顺序，
而玩家心里的队伍是有次序的（谁是二号、三号）。

## 14.4 仓库里状态冻结

`Mon`（持久身份：物种/等级/亲密度）与
[`PetState`](S4-nurture.md)（当前状态：三条轴）分开。

**不给仓库里每只都存三条轴** —— 那意味着 30 只都在衰减，
玩家一周不上线回来发现全体消沉。惩罚性的，
且违反「Tamagotchi 只养一只」的核心体验。

## 14.5 仓库满了不做「放生」

玩家不该被逼着删自己养的东西。

改成替换**重复物种里等级最低的那只** —— 重复个体是唯一
「明确可牺牲」的对象。若没有重复物种则**拒绝捕获**，
让玩家自己去整理。

## 14.6 `resolve_capture()`：唯一的收容入口

「谁负责收容」以前没人负责。现在由它负责，参数刻意收全
（`party` / `dex` / `inventory`）—— 让「捕获会影响哪些系统」
在签名上一目了然，而不是散在调用方各处。

顺序有讲究：

1. **掉落先算** —— 与捕获成败无关（[S9](S9-items.md) 的设计），
   先算避免被第 2 步的早退跳过
2. 收容（可能失败：仓库满且无重复物种）
3. **收容成功才点亮「已捕获」** —— 图鉴不能记下一只实际不在手上的

## 14.7 三键浏览

| 键 | 动作 |
|---|---|
| **A** | 打开操作菜单 |
| **B** | 下一只 |
| **C** | 切换队伍/仓库视图 |

C 给「切视图」而不是「返回」：队伍与仓库是这一页的两半，
在它们之间来回是最频繁的操作。返回放在 A 的菜单里。

菜单项**按上下文变**，不给无效选项：队首没有「设为主宠」、
队伍满时是「与队伍交换」而非「加入队伍」。

## 14.8 字节布局

```
count_party(1) + count_box(1) + 6×8 + 30×8 = 290 字节
```

定长而非变长：变长最多省 288 B，但会让固件侧读写变成两次遍历，
且掉电时半写状态更难恢复。

每只 8 字节：`species(1) level(1) hp(1) intimacy(1) explore(2) nickname(1) flags(1)`
