## 1. 最重要的发现：招式数值也被 retcon 过，且比妖精系隐蔽得多

**`convert_gen1.py` 的 `FAIRY_RETCON` 处理的是同一类问题，但招式这边没人记得。**

PokeAPI 返回的是**现代**数值。实测初代 165 招里 **38 招**在后续世代被改过：

| 招式 | 现代 | 初代 | 危害 |
|---|---|---|---|
| `bite` 咬住 | **恶系** | **一般系** | 恶系在本项目 15 属性表里**不存在** |
| `gust` 起风 | **飞行系** | **一般系** | 同上，属性编号会越界 |
| `karate-chop` 空手劈 | **格斗系** | **一般系** | 属性相克算错 |
| `dig` 挖洞 | 威力 80 | **100** | 伤害偏低 20% |
| `self-destruct` 自爆 | 威力 200 | **130** | 偏高 54% |
| `explosion` 大爆炸 | 威力 250 | **170** | 偏高 47% |
| `leech-life` 吸血 | 威力 80 | **20** | 偏高 4 倍 |
| `low-kick` 踢倒 | 威力 `null`（按体重浮动） | **50** | **会被当变化招整个丢掉** |

`low-kick` 那条最值得记：现代它是「按体重算伤害」所以 `power=null`，
如果只用现代值判断「power>0 才是伤害招」，这招会**静默消失**，
而消失的招式不会报错，只会让某些宝可梦少一招。

**还原方式**：PokeAPI 的 `past_values` 数组按世代升序，每条含义是
「**到该版本组为止**这个字段还是旧值」，所以第一条里的非 null 字段就是初代原值。
数值全部从数据源取，没有一个是手填的（项目惯例）。

### 这个还原依赖一个顺序假设，所以加了运行时校验

「`past_values[0]` 就是初代之后最早的改动」这条假设一旦不成立，
还原出的数值**仍然合法**（威力、属性都在 0~255 内），不会抛异常，只会全都是错的。

所以 `verify_past_values_order()` 每次拉取都实测校验：从 API 拉版本组的世代顺序
（**不手抄** —— 手抄的清单会随新世代发布而过期，过期后校验静默失效），
逐招确认 `past_values` 确实升序、且不含 `red-blue` 自身。本轮 165 招**零违例**。

## 2. 二进制格式

**四段放同一个文件**，因为固件的访问模式是「给定 species_id 与等级，
算出这只现在会哪几招」—— 需要先查学习表拿到招式位置、**再立刻**查招式表拿威力属性，
两段总是一起用。拆成两个文件要维护两个 base 指针，且两者版本会漂移。

全部小端。**下表的字节数由 `struct.calcsize` 在运行时断言过，不可能与实际漂移**
（见第 5 节 —— 这是 `convert_gen1.py` 那次「注释写 28、实际 32」的直接教训）。

### 文件头 16 B

| off | size | field | 实测值 |
|---|---|---|---|
| 0 | 4 | magic | `"MOVE"` |
| 4 | 2 | version | 1 |
| 6 | 2 | move_rec_size | **12** |
| 8 | 2 | move_count | **99** |
| 10 | 2 | species_count | **151** |
| 12 | 2 | learn_count | **607** |
| 14 | 2 | pool_size | **834** |

### 段① 招式表 —— 99 × 12 B = 1188 B，按 move_id 升序紧密排列

| off | size | field | 说明 |
|---|---|---|---|
| 0 | 2 | move_id | PokeAPI 招式 id，1~165 **有缺号** |
| 2 | 2 | zh_offset | 中文名在段④的偏移 |
| 4 | 1 | zh_len | UTF-8 字节数 |
| 5 | 1 | type | **与 `sim/gameplay.py` TYPES 下标一致** |
| 6 | 1 | power | 实测区间 **10~170** |
| 7 | 1 | accuracy | 1~100；**255 = 必中** |
| 8 | 1 | pp | |
| 9 | 1 | damage_class | 0=物理 1=特殊 |
| 10 | 2 | reserved | 预留：附加效果 id、优先度 |

### 段② 物种索引 —— 151 × 4 B = 604 B，按 (species_id − 1) 直接索引

| off | size | field |
|---|---|---|
| 0 | 2 | learn_offset（段③的**条目下标**） |
| 2 | 1 | learn_count |
| 3 | 1 | reserved |

### 段③ 学习表 —— 607 × 2 B = 1214 B，同物种内按等级升序

| off | size | field |
|---|---|---|
| 0 | 1 | level |
| 1 | 1 | move_slot（**段①的下标，不是 move_id**） |

### 段④ 字符串池 —— 834 B，99 个中文名紧密排列

### 三个寻址决策，都为了那一个访问模式

**① 段①紧密排列而非 `(base + move_id*12)` 稀疏索引。**
165 个 id 里只有 99 个是伤害招，稀疏表要按最大 id 开数组，四成槽位是空洞。
紧密排列 + 段③存**段内下标**，固件拿到 slot 就是 `moves_base + slot*12`，
仍是 O(1) 且无空洞。代价是「已知 move_id 反查记录」要二分 ——
但固件不需要这个方向，它永远从学习表出发。

**② 段②按 species_id 直接索引**：`species_base + (species_id-1)*4` 一步拿到 (offset, count)，这是入口。

**③ 段③同物种内按等级升序**：「Lv≤N 的全部招式」就是从 learn_offset
**顺序扫到 level > N 为止**，不必读完整段再过滤，也不必二分。

### 属性编号与 gen1.bin 同一套，且有守护

`type` 直接用 `sim/gameplay.py` `TYPES` 的下标（一般=0 火=1 … 龙=14），
与 `gen1.bin` 的 `type_primary` **同一套**，固件算相克时两边可直接比较，不做二次映射。

这个「必须一致」的要求靠人对着看是守不住的（两个文件相距很远，改一个不会提醒另一个）。
`convert_moves.py` 每次转换都 import `sim/gameplay.py` 逐项比对，
**不一致就中止转换**而不是产出错编号的二进制。已实测：把 TYPES 顺序打乱后转换退出码 1。

> 只读不写 `sim/`，未修改该目录任何文件。

## 4. 交叉验证结果

按要求做了**两轮独立验证**，都不复用转换器的中间变量 ——
复用只能证明「我写的和我想的一致」，硬解才能证明「写出去的和源数据一致」。

### 第一轮：`convert_moves.py` 内置 `crosscheck()`

按文件头声明的偏移硬解二进制，与 `moves.json` 对账。
**全 151 只逐只跑过一遍，零不符**（默认只抽查 8 只，`--verify` 可指定）：

- 段① **99 招逐条**比对威力/属性/命中/PP/中文名 → **全部一致**
- 段②③ **151/151 只**学习表内容与等级顺序 → **全部一致**

#### 这一轮抓到的是**验证器自己的**缺陷

最初默认只查 #1 #25 #150，全绿。把 #6 喷火龙加进去后立刻报错：

```
· #6 charizard 学习表未按等级升序：
  [(1,'scratch'), (1,'ember'), (9,'ember'), (24,'rage'), ...]
```

等级明明是 1,1,9,24… 严格升序。**是检查写错了**：
它拿 `(等级, 名字)` 元组整体比较有序性，于是在同级时额外要求名字也有序 ——
而同级招式在二进制里按 slot 排、在源 json 里按名字排，两者本就不必一致。
固件也只依赖等级升序（扫到 Lv>N 为止），同级顺序无所谓。

改成只比较等级序列后，干净数据通过，**注入真实乱序仍能抓到**（已实测）。
默认 `--verify` 也从 3 只扩到 8 只，含 #6（有同级招）与 #132（零伤害招）两个边界。

记这一条是因为：如果没把 #6 加进去，这个假阳性会一直潜伏，
而它的表现形式是「验证器报错但数据其实是对的」—— 比数据错更容易让人误改数据去迁就检查。

### 第二轮：直接对 PokeAPI 原始缓存 json

绕开 `moves.json`，从 `/tmp/gen1c/cache/*.json` 原始响应重新算一遍：

- 段① 99 招 vs 原始 json（含 `past_values` 还原）→ **不符 0 条**
- 段②③ 6 只 vs 原始 `pokemon_<id>.json` 的 `version_group_details`：

| # | 名字 | 二进制 | 原始伤害招 | 内容 | 等级升序 |
|---|---|---|---|---|---|
| 1 | bulbasaur | 4 条 | 4 条 | ✅ | ✅ |
| 25 | pikachu | 4 条 | 4 条 | ✅ | ✅ |
| 150 | mewtwo | 4 条 | 4 条 | ✅ | ✅ |
| 6 | charizard | 7 条 | 7 条 | ✅ | ✅ |
| 143 | snorlax | 4 条 | 4 条 | ✅ | ✅ |
| 132 | ditto | 0 条 | 0 条 | ✅ | ✅ |

皮卡丘实测：`(1,thunder-shock) (16,quick-attack) (26,swift) (43,thunder)` ——
与 PokeAPI 原始响应逐项相同，无错位。

## 5. `inventory_assets.py` 的断言，以及「断言本身是否有效」

新增 `parse_moves` / `audit_moves` 与 **22 条断言**，覆盖：
magic、定长自洽、头部声明与实测一致（记录数/学习表条数/池大小）、
尾部无多余字节、move_id 无缺号重号且升序、属性与物理特殊标记在合法域、
威力非 0（防变化招混入）、命中在 1~100 或 255、中文名非空、
名字偏移落在池内且解码无乱码、学习表 slot 不越界、等级 1~100 且升序、
无孤儿条目、reserved 为零。

### 绿灯必须能变红，所以做了变异测试

一条永远为真的断言等于没有断言。往 `moves.bin` 注入 12 种缺陷逐一验证：

| 注入的缺陷 | 是否抓到 |
|---|---|
| 头部 rec_size 12→10（**错位**） | ✅ |
| 属性 id=15（恶系混入，越界） | ✅ |
| 学习表 slot=200（越界，会读到别的招） | ✅ |
| 学习表等级乱序 | ✅ |
| 威力=0（变化招混入） | ✅ |
| 命中=0（会被读成永不命中） | ✅ |
| 中文名偏移越出池 | ✅ |
| 中文名偏移切断汉字（乱码） | ✅ |
| 尾部多 8 字节 | ✅ |
| move_id 乱序 | ✅ |
| reserved 非零 | ✅ |
| magic 改坏 / species_count 少 1 / damage_class 非法 / 等级 200 | ✅ |

**12/12 全部抓到，干净数据仍退出 0。**

### 顺带修掉一个「报错方式本身是缺陷」的问题

最初 `rec_size` 被改坏时，脚本抛的是 `struct.error: unpack requires a buffer of 12 bytes`
一行栈回溯 —— 而**错位恰恰是本格式最危险的缺陷**
（读出来全是合法数值，固件不崩，只是全都是错的），它应该得到**最清楚**的一句话，
而不是最晦涩的一句。

现在 `parse_moves` 在解析前先比对头部声明与本文件独立写死的 struct，
不一致就提前中止并输出：

```
· moves.bin 定长不符：头声明 10 B，struct 实测 12 B（照头部写固件会整体错位）
```

中止后 `audit_moves` 返回空，**不再叠加几十条由错位派生出来的假问题** ——
只报根因那一条。

### 格式常量在两处独立写死，是有意的

`inventory_assets.py` 不 import `convert_moves.py` 的常量。
import 过去只能验证「自己和自己一致」，写死才能在两边漂移时报出来 ——
这与该文件原有的设计意图一致（见其模块 docstring）。

## 6. 中文名缺失情况 —— **零缺失，但字库缺 96 字**

**招式中文名 99/99 全部拿到，且全部是 zh-Hans 简体，没有一条走繁体兜底。**
（`move_zh_name()` 仍保留 zh-Hant 兜底路径并会报出数量 ——
繁简混排在 16×16 字库里笔画密度看得出来，将来换数据源时需要知道。）

**但这 178 个用字里，有 96 个还不在 `font16.bin` 里**，需要作为下一步的输入：

```
万乱二伏倒农冲劈十压吨吸咬啄夹射尖居崩强必念怒愤手扎抓拍挖挣掌摔撞攀攻斩旋昏杀束极枪棒
污沫泡洞浊浪涡液溶滚瀑炎炮炸爆牙狱猛环瓣番破神紧线绑绕缠翅翔聚膀膝自舍舔舞血解象踏踢踩
身重锤镖闹雪雾震鞭骨
```

按 16×16 1bpp、单字 32 B 估算，补这 96 字约 **3 KB**，不是瓶颈。

这一条**没有做成断言失败** —— 字库重建是招式入库之后的下一步，
做成硬失败会让本轮永远过不了。但它在 `inventory_assets.py` 通过时也会
以 `⚠️` 显式打印并给出下一步命令，因为真机上的表现是
「招式名那一片是空白」，且要打到那一屏才发现 —— 这正是该文件断言区
记录过的、在一轮开发里重现过三次的那类缺陷。
