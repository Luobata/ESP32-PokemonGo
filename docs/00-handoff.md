## 一、这是什么项目

在一台 **ESP32-C3 掌机**上做宝可梦风格的真实世界探索游戏，自用、不分发。

硬约束（见 [01-constitution.md](01-constitution.md)）：

| 项 | 值 | 后果 |
|---|---|---|
| 屏幕 | 240×320 彩色 | 整帧 RGB565 = 150 KB，**装不下**，必须分块横带渲染 |
| 按键 | **只有 A/B/C 三个** | 所有交互的第一约束。取名、翻页、导航都受它限制 |
| SRAM | ~400 KB | 上面那条的原因 |
| flash | 8 MB | 宽裕。资产才用了 149 KB |
| **无 GPS** | | 用 WiFi 环境指纹替代 —— 这是整个项目的技术核心 |
| **无 IMU** | | **步数不可实现**，所以用「移动量」而非步数 |
| 无内置 DAC | | 音频只能 PWM 或 I2S，指向实时 chiptune 合成 |

核心设计取向（[02-sensing.md](02-sensing.md#20)）：
**让时间生产内容，让空间调制内容** —— 任何基于「见到新 BSSID」的指标都会衰减到零，
所以驻留也要有产出（基地按时间排程），出门只是更快（猎场按瞬现 AP）。

```bash
python3 -c "
import sys; sys.path.insert(0,'sim')
```

### P1 — 已知缺陷，有数据支撑

**③ 三个模块仍无人调用**

```
audio     只被 build.py 读参数 —— orchestrate 该在遭遇/捕获/进化时播音效
pixelart  同上 —— 开场与捕获页要画精灵球
strings   同上 —— 所有 UI 文案该从它取，而非散在各处字面量
```

这是上一轮串联发现「8 个孤岛」后剩下的。修法同 S19：在 `orchestrate.py`
里真的调用它们，而不只是导出参数给页面看。

**④ S19 缺文档**

`docs/systems/` 只有 S1~S18。`08-systems.md` 的索引也没加 S19。

**⑤ 商业区访问速率是估的**

第 6 馆要「去商业区 4 次」，我按「每周 2~3 次商场」估成 0.4 次/天 → 10 天。
**但真实采集数据里商业区只占 0.8%，19.9 小时内一次都没确认过访问。**
这个数没有实测支撑，要用更长的真实数据验证。

**⑥ 交通枢纽等 BLE**

`classify_biome` 的交通枢纽分支要 `ble_count > 10`，而采集工具不输出 BLE、
5 处调用全不传 —— 是死代码。ESP32-C3 有 BLE，固件阶段能扫到时它会自动开始工作，
那时第 6 馆可以改回绑它（现在绑商业区）。

PC 侧若要提前验证，得给 `tools/collector` 加 BLE 扫描。

### P2 — 需要真机

| 项 | 卡住了什么 | 怎么测 |
|---|---|---|
| 续航天数 | 扫描频率上限 → 遭遇频率、地点时间分辨率 | 实测电流曲线 |
| RTC 走时精度 | 状态轴是「小时」级还是「天」级；S10 日切判定 | 深睡 12 小时对比 |
| 外置 32.768kHz 晶振 | 同上 | 拆机目视或实测漂移 |
| NFC 芯片型号 | 能否用 NFC 对时 | 手机 NFC Tools 读 |
| 口袋 RSSI 基线 | 阈值标定 —— 现在用的是电脑天线数据 | 装兜里对比桌面 |
| 音频通路 PWM 还是 I2S | S13 的输出方式 | 规格表只写「扬声器」 |
| 是否有耦合电容 | 决定去直流是必需还是保险 | 拆机或实测 |

固件实现顺序见 [07-roadmap.md](07-roadmap.md) 的 F1~F14。
**F5 是关键一致性检验**：把 `data/raw/*.ndjson` 灌进固件，
它应当算出与 `sim/replay.py` 完全相同的状态序列。

## 四、这轮修掉的缺陷（避免重复踩）

全都是**只有把系统串起来跑真数据才会暴露**的：

| 缺陷 | 根因 | 教训 |
|---|---|---|
| 捕获成功后宝可梦实体消失 | 只点亮图鉴 bit，没有队伍容器 | 玩法的产出必须有地方去 |
| `Inventory.use()` 全项目零调用 | 文档写了规则，代码只实现一半 | 投球不扣球、喂食免费 |
| 第 6 馆需 3400 天 | 门槛按 biome 平均分配，真实分布极度不均 | 稀有 biome 不能用「累计小时」衡量 |
| 办公环境 17% 判成野外 | `classify_biome` 缺 AP 下限保护 | **稀疏扫描不可信** —— 同 `MIN_APS_FOR_DISTANCE` |
| 交通枢纽从未被判出 | 要 BLE 计数，但采集不输出、调用不传 | 死代码：分支存在 ≠ 会执行 |
| 等级上限表错位一格 | 当成「持有 N 枚时」而非「取得后」 | 四个道馆数学上打不过 |
| 队伍数据凭记忆手填 | 坂木错两处、阿渡错一处 | 数值必须从反汇编源头取 |
| 字库丢了 151 只中文名 | 依赖 `/tmp` 中间文件，清磁盘时删了 | 字库改从 `assets/gen1.bin` 读 |
| 星光镜像赋值长出杂散点 | 双循环 `g[c+i][c+j]` + `g[c+j][c+i]` | 点阵要看 ASCII 预览，不能只看统计 |
| 精灵球矢量圆与像素画打架 | `canvas.arc()` 没有台阶感 | 用户一眼看出「画面太生硬」 |

## 六、几条容易忘的项目惯例

- **数值不手填**，从 pret 反汇编取（`data/trainers/parties.asm` 等）
- **页面改动要真开浏览器验**，`node --check` 通过不代表画对了
  （栽过：网格渲染成单色、精灵球画成矢量圆、星星形状错）
- 提交消息用 `git commit -F 文件`，正文里的 `"<HBB..."` 会被 shell 当命令替换
- 中文名用**任天堂官方译名**（zh_nin），不是动画代理译名
  （徽章是**颜色名**：灰色徽章而非岩石徽章，从英文回译八个全错）
- 字库改完要跑 `convert_font.py` 并验证 151 物种名 + UI + 昵称 + 台词都渲染得出
- `docs/pages/` 是**生成的**，改文案要改 `sim/strings.py` 再跑 `gen_pages.py`
